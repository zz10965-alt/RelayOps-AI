# RelayOps AI — Codex 项目总指令

你是本项目的 Tech Lead、AI 应用工程师、全栈开发工程师和测试工程师。请直接在当前 GitHub 仓库与 Codex Cloud 工作区中工作，并用中文解释关键决策和阶段成果。

## 1. 项目目标

**项目名称：** RelayOps AI  
**定位：** Multimodal E-commerce Operations Agent（多模态电商运营异常处理智能体）

开发一个真正可运行的 AI Agent：接收客户文字和商品照片，查询业务系统与售后政策，调用工具执行允许的操作，更新任务状态、验证结果，并在信息不足或无法自动解决时转交人工。

这不是简单的聊天机器人、图片识别器或静态网页。项目重点展示：Dify 工作流编排、多模态模型调用、API 集成、端到端任务执行、异常处理、结果验证和自动化效果评估。风险控制是必要的工程保障，但不是项目主卖点。

## 2. MVP 范围

先完整实现一个场景：**商品损坏售后处理**。

用户提交订单号、问题描述和商品照片，系统需要：
1. 分析文字与图片，提取关键字段；
2. 查询模拟订单、商品信息和售后政策；
3. 检查资料是否完整及是否符合明确业务规则；
4. 符合条件时调用 API 创建退货申请；
5. 信息不足时请求补充，无法自动解决时转交人工；
6. 再次查询业务状态，验证申请是否真实创建；
7. 保存工具调用日志和任务执行记录。

必须区分“AI 建议处理”“申请已创建”“申请已批准”和“退款/退货已完成”。不能仅凭模型文本宣称任务成功。

核心场景跑通后，再评估扩展物流延迟、库存与履约异常，不要第一阶段同时开发所有场景。

## 3. 技术方案

优先采用：
- **Dify Workflow**：模型调用、知识检索、条件分支和工具编排；
- **支持图像输入的多模态模型**：处理文字与照片；
- **Python + FastAPI**：实现可执行的模拟业务 API；
- **SQLite**：保存订单、退货申请、任务状态和日志；
- **React/Next.js + TypeScript**：开发专业的 Web Demo；
- 自动化测试及 Git 版本管理。

先检查当前 Dify 版本、模型能力和环境限制，确认所选模型与工作流节点支持图像输入。采用简单清晰的模块化架构，不要无必要地引入微服务或多 Agent。

## 4. Demo 要求

开发专业的企业 SaaS Dashboard，而不是普通聊天界面，至少包括：
- Overview：真实任务统计与状态；
- New Case：订单号、文字描述和图片上传；
- Case Detail：订单信息、提取字段、政策依据及缺失资料；
- Execution Trace：真实工作流步骤、工具调用、返回值和错误；
- Resolution Result：申请实际状态；
- Human Handoff：需人工处理的任务；
- Evaluation Dashboard：根据真实日志计算的指标。

前端必须调用真实后端与 Dify 工作流，不能用静态假数据冒充成功结果。Dify API Key 只能放在服务端环境变量或受保护的配置中，禁止暴露在前端或提交到 GitHub。

## 5. 分阶段执行：先 Plan，再实施

首先检查当前仓库、分支、文件、可用命令、运行环境和依赖。不要覆盖或删除已有工作。创建以下项目管理文件：

- `AGENTS.md`：开发规范与安全要求；
- `PLANS.md`：阶段计划、依赖及验收标准；
- `progress/build-log.md`：执行记录与测试证据；
- `PRD.md`：产品需求；
- `ARCHITECTURE.md`：系统架构；
- `workflow_design.md`：Dify 工作流设计；
- `API_SPEC.md`：模拟 API 规范；
- `evaluation_plan.md`：测试和评估方案。

之后按以下阶段推进：

**Phase 1 — 规划：** 明确用户流程、MVP 范围、工作流节点、API、数据模型、验收标准和测试案例。完成文档检查后继续下一阶段。

**Phase 2 — Dify 最小工作流：** 生成当前版本尽可能兼容的 DSL YAML，先验证输入、模型分析、结构化输出和错误处理，再逐步增加工具调用。明确区分文件已生成、已导入、节点已测试和端到端已验证。

**Phase 3 — 模拟业务 API：** 使用 FastAPI 和 SQLite 实现订单/商品查询、政策查询、退货申请创建、申请状态查询及执行日志。创建记录后必须可再次查询。处理无效订单、缺失字段、重复提交、超时和异常响应。

**Phase 4 — 端到端集成：** 在 Dify 中通过 HTTP Request 或合适的工具节点连接业务 API。测试真实查询、申请创建、状态验证、有限重试和人工交接。

**Phase 5 — Web Demo：** 开发上述页面，并连接真实后端与工作流；显示真实加载、成功、失败和待处理状态。

**Phase 6 — 测试与作品集：** 测试正常申请、模糊/无关图片、订单不存在、信息冲突、资料缺失、政策不符合、API 失败、重复提交及人工交接。完善 README、架构图、工作流配置、测试报告和演示说明。

## 6. 评估指标

至少计算：端到端任务完成率、自动完成比例、工具调用成功率/参数正确率、平均处理时间、失败恢复情况、人工介入比例和单次 API 成本。指标必须根据真实运行日志和测试结果计算，不得提前编造准确率、效率提升或商业 ROI。明确标记合成数据和模拟系统的范围。

## 7. 每阶段执行规则

1. 每次开始阶段前读取 `AGENTS.md`、`PLANS.md` 和开发日志。
2. 说明本阶段目标和验收标准，然后直接执行可安全完成的工作，不要只给建议。
3. 运行测试，修复问题并重测；将实际修改、测试命令、结果、未完成项和阻塞更新到计划与日志。
4. 每阶段结束时用中文简要汇报，并自动继续下一个未受阻阶段，不要每个小步骤都等我确认。
5. 若必须由我登录/授权 Dify、配置模型凭据或执行外部发布，暂停该步骤，明确说明最少必要操作；继续做其他不受阻任务。
6. 不要假装已创建文件、导入 DSL、调用模型、运行测试或发布成功。不得覆盖已有工作、泄露凭据、提交秘密信息或擅自进行破坏性操作和未经授权的外部发布。
